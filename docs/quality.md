# Качество сервиса: замер

Что проверяли: отбирает ли сервис нужные события, опирается ли карточка на источники, сходятся ли числа ленты и
карточки, по теме ли позиция Альфа-Банка, нет ли выдуманных чисел и имён, сколько стоит и длится разбор и что
сервис делает с новостями, которых не видел. Всё считается автоматически одной командой; где нужен смысловой
вердикт — его выносит судья (разрешённая модель), а выборку его разметки мы проверили вручную.

## Что нашли

Замер на 40 свежих новостях и 5 пользователях. Главное — отбор пропускает касающиеся события.

- **Отбор пропускает нужное.** Из 10 событий, которые судья признал касающимися, в ленте с оценкой ≥ 0,3 только 3.
  Примеры: дизель и поставки в США (владелец топливного холдинга), «Трамп: Россия дала нефть…» (тот же
  пользователь) — в ленте не попали. Полнота 30 %, это главная слабость. Точность «касается» 43 % — выборка
  из 7 показанных событий, на ней процент шаткий.
- **Ошибка 503 на черновике.** Событие `src:news:1e0bd1023d32` для финдиректора не собралось: ответ модели
  DeepSeek не прошёл проверку схемы на шаге «draft». Для других пользователей то же событие собралось.
  Значит, сбой валидации ответа, а не отказ по теме; сервис честно вернул 503, но карточки нет.
- **Выдумки почти нет по числам, но проверка узкая.** 3 из 227 чисел в 2 из 20 карточек не нашлись ни в данных,
  ни в источниках. Имена: 33 кандидата, в основном обычные слова с заглавной буквы; вручную не разбирали.
- **«Опора на источники» — 92 %, 11 утверждений без опоры.** Проверяется, что ссылка находится (признак, фактор
  карты или материал банка) и число есть в ней, а не что утверждение следует из источника по смыслу. Ссылки на группу,
  цепочку и платежи не засчитываются, поэтому часть честных утверждений тоже попала в «без опоры».
- **Позиция банка по теме — 80 %.** Из 30 утверждений банка 6 не о том факторе, что событие (судья). Примеры
  в детальном разделе ниже.
- **Выборка мала.** 40 новостей и 10 касающихся — проценты с ±15–20 п.п. Перед сдачей повторить на большем
  наборе.



## Как устроен замер

**Набор** — `apps/api/eval/cases.json`:

- **5 пользователей** разных ролей и отраслей: собственник топливного холдинга (`p-u57706-owner`), финдиректор
  оптовика автозапчастей (`p-u8318-cfo`), казначей зернотрейдера (`p-u34911-tre`), гендиректор поставщика общепита
  (`p-u258116-ceo`), главбух энергетической компании (`p-u190452-acc`).
- **40 свежих новостей из базы**, без ручного отбора: 20 последних деловых новостей до 26.10 03:00 МСК и 20
  следующих за ними, у которых разметка нашла хотя бы один фактор. Список зафиксирован в наборе.
- **6 эталонов**: пять пересказанных образцов (ставка 14 % для финдиректора, главбуха и собственника,
  замедление потребления для поставщика общепита, недельная дефляция для зернотрейдера) — текст события
  пересказан своими словами, к каждому чек-лист из 3–5 пунктов; шестой — решение ЦБ 23.10.2026 из базы, которого
  в образцах нет (проверка, что сервис не выдаёт прогноз банка от 11.09 за новый).
- **8 новостей, которых сервис не видел**: написаны для замера и подаются как «своя новость» — по отрасли клиента,
  через покупателей, сырьё, не по теме (футбол), на английском, с инструкцией внутри текста, шум из трёх слов,
  налоги для главбуха.

**Стенд.** Отдельный стек `docker compose -p eval` на своих портах (API 8010, БД 5443) из того же кода, с копией
новостей из базы общего стенда; общий стенд только читался. Карточки собраны с нуля, кэш стенда был пуст.

**Судья** — Qwen3.6 35B A3B: в этом прогоне сервис её не вызывал (разборы шли на Gemma и DeepSeek), поэтому судья не оценивает
свои же ответы. Модель остаётся запасной для Gemma в самом сервисе — это надо помнить при повторе замера. Ответы судьи кэшируются локально в `apps/api/eval/cache/judge/` (в git не попадают) — повторный прогон на
том же стенде бесплатный и даёт ту же разметку.

**Как считается каждая метрика**:

1. **Отбор.** Решение сервиса — лента пользователя (`/api/feed`, до 100 событий): «касается», если у события оценка
   ≥ 0,3 (ниже интерфейс сворачивает его в «ещё N меньшей значимости»), иначе «не касается». Правильный ответ —
   разметка судьи по карточке компании из данных банка (отрасль, продукты, группа, отрасли покупателей и
   поставщиков); карту чувствительности сервиса судья не видит. Точность «касается» — доля верных среди показанных,
   точность «не касается» — доля верных среди скрытых.
2. **Опора на источники.** Утверждения с меткой «факт», «банк», «данные», позиция банка одной фразой и цитаты.
   Подтверждено, если ссылки есть, каждая находится через API (`/api/sources`, профиль и карта компании), каждое
   значимое число текста есть в материале по ссылке, а цитата дословно есть во фрагменте. Смысл утверждения без
   чисел не проверяется — только то, что ссылка настоящая. Поля `claims` в контракте пока нет, поэтому проверка
   своя.
3. **Числа охвата.** Для событий из ленты сравниваются лента и карточка: уровень вывода (важно / следить / к
   сведению), счёт компаний группы («N из M компаний») с расчётом охвата группы и числа из вывода ленты в тексте
   карточки.
4. **Позиция банка.** Для каждого утверждения банка судья решает, о том же ли факторе оно, что событие. Где
   карточка говорит «позиции нет», судье дают до 8 свежих фрагментов аналитики банка с теми же факторами — была
   ли позиция, которую стоило показать.
5. **Выдумки.** Числа во всех текстах карточки (кроме расчётов с меткой «оценка»), которых нет нигде в данных:
   профиль и карта компании, охват группы, цепочка, лента, первоисточники, текст новости. Даты, годы, коды
   материалов и целые до 10 не считаются. Названия и имена с заглавной буквы, которых нет в данных, — кандидаты,
   их не разбирали вручную. Метрика осторожная: случайное совпадение числа с чем-то в данных засчитывается как
   «есть», поэтому выдумок может быть больше, чем найдено, но не меньше.
6. **Время и стоимость.** Время — от запроса до готовой карточки для каждой новой сборки; стоимость — сумма по
   вызовам моделей в трассе сборки. Ниже — ещё и журнал вызовов моделей стенда по шагам.
7. **Устойчивость.** Что сервис ответил на каждую новую новость и сколько в карточке чисел без опоры.

## Как повторять регулярно

Цель — видеть, не стало ли хуже после правок. Прогон сравнивает таблицу с прошлой и пишет регрессии.

- **Команда:** `python apps/api/eval/run.py --api http://127.0.0.1:8010` (стенд `docker compose -p eval`).
  Повтор без моделей: `python apps/api/eval/run.py --offline`. Разборы из прошлого прогона того же набора не
  пересобираются (кэш); `--rebuild` — пересобрать.
- **Когда:** после каждого изменения агента, отбора или ранжирования; перед заморозкой кода — обязательно.
- **Пороги регрессии** (относительно прошлого прогона на том же наборе):
  - полнота и точность «касается» — падение больше 10 п.п. → регрессия, разобрать до слияния;
  - доля подтверждённых утверждений — ниже 95 % → регрессия;
  - выдумки чисел — рост числа карточек с выдумками → регрессия;
  - ошибки 503 на разборе — рост доли сбоев выше 5 % → регрессия;
  - время медианы разбора выше 60 с или стоимость медианы выше 1 ₽ → предупреждение.
- **Что делать:** регрессия — issue с меткой `баг` на владельца зоны (отбор — бэк, карточка — агент,
  интерфейс — фронт), с примером из раздела «Подробно» и номером прогона.
- **Журнал:** прогоны пишутся в `apps/api/eval/results/latest.json`; предыдущие — копировать в `results/` с датой
  перед повтором, чтобы сравнивать.

## Как повторить

```bash
# стенд замера на своих портах; ключ моделей — в .env
API_PORT=8010 DB_PORT=5443 docker compose -p eval up -d --build
# (для того же набора новостей — скопировать таблицы news, news_business, news_image_stubs из основной базы)
python apps/api/eval/run.py --api http://127.0.0.1:8010
# только пересчитать таблицу из сохранённых ответов, без API и моделей
python apps/api/eval/run.py --offline
docker compose -p eval down -v
```

Нужен только Python 3.12, зависимостей нет. Сырые ответы прогона — `apps/api/eval/results/latest.json`; таблица
выше и в README вписывается скриптом между метками. Лимиты прогона: 22 ₽ на сборку карточек и 6 ₽ на судью.
